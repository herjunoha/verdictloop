An improvement loop for AI agents and chatbots

A coding agent edits your agent, a fixed set of conversations scores the edit, and the edit is kept only if it is really better. Every change gets one of four verdicts, because a chatbot's score moves by luck.

loop

An improving agent, such as Claude Code reading program.md, repeats the same five steps. verdictloop does the measuring and the keeping or reverting.

project

Everything lives in one folder, and all state is in files, so a fresh agent session can pick up at any time.

eval/ and verdictloop.toml are fingerprinted when the baseline is taken. If either changes afterwards, try refuses to run, so the agent cannot move the goalposts.

target

The target is whatever you want to improve: a prompt, a config file, tool descriptions, code. [target] files lists what the agent may edit.

Your agent is reached through one command that answers one turn. It can be a few lines that call a model with your prompt, or a few lines that call a deployed service. verdictloop never needs to know which.

  • messages is the whole conversation so far, so a stateless wrapper works. A stateful agent can key its session on conversation_id.
  • events is what the agent did besides talk: a tool call, a handover, a flag. Checks can require or forbid them.
  • metrics are numbers the agent reports, such as a confidence. Checks can bound them.
  • trace says why the agent did what it did. It is shown to the improving agent so it diagnoses from evidence.
  • If edits must be pushed somewhere before they take effect, [target] setup runs a command before every pass. Point it at a development copy, never production.

eval

The eval is a set of scripted conversations, split in two. The improving agent sees and optimizes against tuning.json. It never sees heldout.json, which exists to catch edits that only help the tuning scenarios.

Checks

  • present and absent: a regex, or a named set from patterns.json, over the reply text. A set can list negation terms so "I can't guarantee" does not count as a promise.
  • event and no_event: something the agent did, or must not do.
  • metric: a reported number within bounds. max_seconds: a reply within a time the engine measures itself.
  • turn limits a check to one reply. Without it the check looks at every reply.
  • An optional judge model covers only what a rule cannot decide. It gets its own prompt and facts, which the agent under test never sees.

Scoring

A scenario scores the share of its checks that passed, and a set scores the mean of its scenarios. A scenario that half works earns half credit, so progress shows before a scenario fully passes. opening is what the agent says first, for broadcasts or greetings; it is shown to the agent and never scored. tag names a known weakness a scenario probes, which lets the loop warn when one group gets worse.

verdict

baseline runs the eval three times on the unchanged target. The spread of those runs is the noise. The noise band is the larger of two standard deviations and one scenario, so a single scenario flipping is never evidence.

After try runs the eval three times on the edited target, the verdict comes from this order of questions.

  1. Did fewer than two passes finish? INFRA_FAIL The run broke. Nothing is decided and broken runs are never counted as zero.
  2. Is the tuning score below the band? REFUTED Worse. The target is put back.
  3. Is it inside the band? NEUTRAL Indistinguishable from luck. The target is put back.
  4. Above the band: is the held-out score worse than its own band? REFUTED Better on tuning, worse on held-out, which is overfitting.
  5. Otherwise VALIDATED The edit is kept and its passes become the new baseline.
  • VALIDATED
  • NEUTRAL
  • REFUTED
  • INFRA_FAIL

session

Each try prints one block the improving agent reads, and appends one line to results.tsv.

last_eval.md is rewritten after every run. For each tuning scenario that did not fully pass it shows the failed checks, the conversation with its events and metrics, and the trace. Held-out scenarios never appear in it, so the agent can read it freely.

A session over time

Keeping the loop honest

  • reseed re-measures the kept target and makes that the baseline. A kept edit was chosen because it scored well, partly by luck, so the bar it leaves can be too high.
  • status shows the tuning and held-out scores of the kept target and their gap. A large gap means overfitting. It also shows how much the target has grown, since a prompt that only ever gets longer is a warning sign.
  • Stop rules, chosen when the baseline is taken: a maximum number of tries, a target score, and a patience for tries in a row without progress. When one is reached, try prints SESSION COMPLETE and refuses further tries.
  • token cap in the config stops the loop when your commands report that many tokens.

run

The offline demo is a fictional library help desk with a deterministic stand-in chatbot, so it runs with no model and no key.

To use it on your own agent, write the target command, the scenarios and a program.md, then run baseline. Read the noise band it prints and its warnings: no room to improve means the eval is too easy, and no room to fall means a bad edit could not be shown worse. Calibrate once with a deliberately bad edit and a blank-line edit. The full guide is in README.md, and examples/offline_demo/program.md is a complete instruction file.

Limits

  • The fixed-eval check is a fingerprint, not a lock. It stops silent changes to the eval but not edits to the engine itself. Run the engine installed, outside the agent's reach, if that matters.
  • The held-out set is hidden by convention. The agent can read heldout.json and the raw logs if it ignores program.md.
  • Three passes is the minimum for a noise band. A wide band means more repeats or more scenarios.
  • Results hold only for the setup measured: one target, one configuration, small numbers.
